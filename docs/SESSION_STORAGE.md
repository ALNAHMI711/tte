# تخزين جلسات تسجيل الدخول

## الخيارات الحالية

يوفر المشروع مخزنين:

- `SessionStore`: ذاكرة العملية الواحدة للاختبارات والتطوير فقط. تضيع الجلسات عند إعادة التشغيل، ولا تتشاركها عمليات Uvicorn المتعددة.
- `SQLiteSessionStore`: تخزين دائم على قرص محلي، ويمكن لعمليات متعددة على المضيف نفسه مشاركة الجلسات والقدرة على إبطالها.

## استخدام SQLite على مضيف واحد

أنشئ المخزن ثم مرره إلى خدمة المصادقة عند تركيب التطبيق:

```python
from trading.auth import AuthenticationService, UserCredential
from trading.session_store import SQLiteSessionStore
from trading.api import create_app

sessions = SQLiteSessionStore(
    "/var/lib/tte/sessions.sqlite3",
    ttl_seconds=3600,
    step_up_seconds=300,
)
auth = AuthenticationService(credentials, sessions=sessions)
app = create_app(auth)
```

يجب أن يكون المجلد `/var/lib/tte` مملوكاً لمستخدم تشغيل التطبيق وبصلاحيات مقيدة، وأن يكون على قرص دائم محلي. لا تضع قاعدة الجلسات داخل مستودع Git أو مجلد الملفات الثابتة، ولا تشاركها عبر NFS.

## حدود النشر

- SQLite هنا لمضيف واحد فقط؛ لا تستخدمه لمشاركة الجلسات بين عدة خوادم.
- عند الانتقال إلى عدة مضيفين، استخدم مخزناً مشتركاً مثل PostgreSQL أو Redis مع TTL وإبطال ذري للجلسات.
- لا يزال محدد محاولات تسجيل الدخول الحالي داخل ذاكرة العملية؛ لذلك لا تعتبره حماية موزعة ضد التخمين حتى يتم نقله إلى مخزن مشترك مع تحديد المعدل حسب الحساب وعنوان العميل.
- لا يُعد وجود مخزن SQLite وحده دليلاً على جاهزية الإنتاج؛ يلزم إعداد النسخ الاحتياطي والتشفير على مستوى القرص وإدارة الأسرار ومراقبة الوصول.
- لا تفعّل LIVE اعتماداً على نجاح اختبارات الجلسات وحدها.
